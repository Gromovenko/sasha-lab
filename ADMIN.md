# Раздел /admin и кабинет клиента

Одно место, где видно всё хозяйство студии, и нормальный вход в него: люди,
роли, сессии, восстановление пароля, журнал событий. Плюс личный кабинет
клиента `/cabinet`.

Прежние панели (`/crm` — мастер, `/seo` — владелец) остаются рабочими столами и
подчищаются постепенно: их экраны открываются из админки ссылками, а вход стал
общим — сессия `/admin` пускает и в `/crm`, и в `/seo` (никакого второго пароля).

## Что где

| Адрес | Кому | Что |
|---|---|---|
| `/admin/` | сотрудник | сводка: заявки, вопросы, спрос, люди, ошибки за сутки |
| `/admin/deals`, `/admin/deal?id=` | сотрудник | все заявки и карточка (ответ клиенту — в `/crm`) |
| `/admin/clients`, `/admin/client?id=` | сотрудник | клиенты, их заявки и журнал |
| `/admin/questions` | сотрудник | вопросы с сайта (ответ публикуется из `/seo/q`) |
| `/admin/knowledge` | сотрудник | база знаний, спрос, прогоны сбора |
| `/admin/parsers` | сотрудник (кнопки — администратор) | парсеры: по источнику документы, последняя запись, статус; запуск/остановка сбора через общий замок |
| `/admin/users` | администратор | доступы: создать, роль, блокировка, ссылка на пароль, закрыть сессии |
| `/admin/log` | сотрудник | единый журнал: вход, действия, прогоны, ошибки |
| `/admin/services` | сотрудник | что подключено: база, миграции, каналы, ключи |
| `/admin/profile` | все | свой пароль и свои сессии |
| `/admin/api/summary.json` | сотрудник | та же сводка машиночитаемо |
| `/admin/api/parsers.json` | сотрудник | идущие сборы (замки, процессы) и цифры по источникам |
| `/cabinet/` | клиент | свои заявки, расчёт, переписка, сообщение студии |
| `/cabinet/register`, `/cabinet/login`, `/admin/forgot`, `/admin/reset` | все | вход и восстановление |

## Роли

`владелец` → всё, включая роль владельца · `администратор` → данные, доступы
(кроме владельца) · `мастер` → заявки, цены, знания · `клиент` → только свой кабинет.

Клиент в админку не попадает физически: его уводит в `/cabinet`, и наоборот.

## Первый запуск

1. `npm run migrate` — накатывает `005_admin.sql` (люди, сессии, сбросы, журнал,
   `deals.client_user_id`).
2. Откройте `/admin/` — пока служебных учёток нет, там форма «Первый вход».
   Если в окружении остался прежний пароль панелей (`ADMIN_PASSWORD` или
   `SEO_ADMIN_PASSWORD`), форма попросит и его. После создания владельца форма
   исчезает навсегда.
3. Дальше люди заводятся из `/admin/users`: человеку уходит ссылка «задайте
   пароль». Пароля не видит никто, включая владельца.

Без веба то же самое делает CLI (нужен, когда не настроен ни один канал доставки):

```bash
node admin/cli.js create --name Саша --email owner@sasha-lab.ru --role owner
node admin/cli.js reset-link owner@sasha-lab.ru --url https://sasha-lab.ru   # ссылка в консоль
node admin/cli.js list          # кто есть
node admin/cli.js kick <логин>  # закрыть все его сессии
node admin/cli.js log --level error --limit 50
node admin/cli.js purge --days 180   # чистка журнала и протухших сессий (крон)
```

## Как устроен вход

* пароль — scrypt-хэш со своей солью на запись, сравнение `timingSafeEqual`;
* сессия — строка в `app_sessions`, в куке только токен, в базе его **хэш**:
  из базы нельзя достать ничего, чем можно войти;
* «выйти на всех устройствах», блокировка человека и смена пароля выбивают
  сессии немедленно — это и есть причина держать сессии в базе, а не в подписи;
* 5 промахов подряд → блок на 15 минут; ответ на неизвестный логин не отличается
  от ответа на неверный пароль ни текстом, ни временем;
* восстановление: одноразовый токен на 60 мин, в базе хэш, доставка по лестнице
  почта → СМС → WhatsApp (первый настроенный канал). Не ушло ничем — ссылка
  пишется в лог процесса, а форма всё равно отвечает «если контакт известен,
  ссылка отправлена»: иначе она работает как справочник клиентов студии.

Настройки: `ADMIN_SESSION_DAYS` (14), `ADMIN_RESET_MINUTES` (60),
`ADMIN_LOG_DAYS` (180), `ADMIN_LOG_CONSOLE=0` — не дублировать журнал в stdout.

## Кабинет клиента

Учётка клиента заводится **сама** в момент заявки с сайта: контакт уже оставлен,
пароля нет. Человек нажимает «забыли пароль» (или получает ссылку от мастера) и
попадает в свои расчёты. Регистрация вручную (`/cabinet/register`) подтягивает
прежние заявки по тому же контакту.

В кабинете видно только отправленное: черновики ответов и заметки мастера —
не его дело. Сообщение из кабинета падает в ту же переписку и запускает пересчёт.

## Журнал

Одна таблица `app_events` на все контуры (`auth`, `admin`, `cabinet`, `crm`,
`engine`, `seo`, `harvest`, `system`), уровни `debug|info|warn|error|security`.
Писать из любого модуля:

```js
const log = require('./admin/log');
await log.info({ area: 'engine', action: 'deal.sent', entity: 'deal', entityId: id, message: '…' });
await log.around({ area: 'harvest', action: 'crawl' }, () => crawl(src));  // успех/падение + длительность
```

Журналирование никогда не роняет вызывающего: упавшая запись — строка в stderr.
Всё дублируется в stdout процесса (`pm2 logs sasha-lab`), потому что базы может
не быть, а событие «кто-то подбирает пароль» обязано остаться хоть где-то.

## Парсеры

`/admin/parsers` — таблица по источникам реестра (`harvest/sources.js`): документов
в базе, прибавка за сутки, дата последней записи и статус (`идёт` / `свежий` —
писали не позже 8 дней назад / `давно` / `пусто` / `выключен`). Хост ведёт на хвост
его лога `/var/log/sashalab-harvest/<host>.log`.

* «Идёт ли сбор» определяется не флажком, а замком: держатели
  `/tmp/sashalab-harvest*.lock` ищутся через `/proc/*/fd` (дочерние `node
  harvest/run.js crawl` наследуют дескриптор). Отдельные замки
  (`sashalab-harvest-<имя>.lock`) тоже видны и гасятся.
* «Запустить» зовёт ту же `scripts/harvest-queue.sh` под общим замком — память,
  nice/ionice и «один сбор на сервер» остаются там. Пока общий замок занят, новый
  запуск не принимается. Очередь отвязывается `setsid -f`: pm2 на рестарте гасит
  дерево потомков, и иначе выкат сайта убивал бы сбор. Вывод очереди —
  `/var/log/sashalab-harvest/queue-admin.log`.
* «Остановить» — SIGTERM держателям замка и их группе процессов, через 10 с
  SIGKILL оставшимся. Собранное уже в базе, повторный запуск продолжит с обрыва.
* Кнопки — администратор и владелец; мастер видит таблицу. Каждое действие
  пишется в журнал (`area=harvest`, `parsers.start` / `parsers.stop`).
