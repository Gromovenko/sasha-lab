# sasha-lab — статическое зеркало сайта sasha-lab.ru

Полная копия публичного сайта студии автотюнинга «Дядя Саша» (Ростов-на-Дону),
снятая 08.09.2026 для анализа и дальнейшей работы. Оригинал — на Tilda за DDoS-Guard.

## Админка и кабинет клиента — `ADMIN.md`

С 18.09.2026 у проекта есть раздел **`/admin`**: сводка по всем контурам (заявки,
клиенты, вопросы, спрос, службы), учётные записи с ролями, журнал событий и
восстановление пароля. Клиенту — кабинет **`/cabinet`** со своими заявками и
расчётами. Вход общий: сессия `/admin` пускает и в `/crm`, и в `/seo`.
Первый владелец заводится на `/admin/` после `npm run migrate` (или
`node admin/cli.js create --role owner`). Подробности — в `ADMIN.md`.

## Движок заявок и автостраницы — `ENGINE.md`

С 17.09.2026 в репозитории два новых контура, оба универсальные (отрасль задаётся
файлом `packs/<id>.json`, кода не касается):

* **`engine/`** — обращение клиента → разбор переписки → зрение по фото → смета →
  готовый ответ с ценой → отправка в канал → напоминания. Панель мастера `/crm`,
  публичная форма `/zayavka`, ручка `/api/lead`, фоновая служба `engine/worker.js`.
* **`seo/lib/writer.js`** — автостраницы базы знаний по свежему спросу, с
  проверкой обоснования и запретом выдуманных цифр (`node seo/cli.js autopages`).

Подробности, раннбук и список ключей, которые осталось подключить, — в `ENGINE.md`.
Быстро посмотреть, что получает клиент, без базы и без ключей:
`node engine/cli.js demo --finding tight_space`.

## Что изменено относительно оригинала
Сырое зеркало «как есть» лежит в первом коммите (`23a8535`). Во втором коммите:
1. Все `https://static|neo.tildacdn.com/…`, `https://fonts.gstatic.com/…` переписаны
   на локальные `/cdn/<хост>/…`; ссылка на Google-Fonts CSS → `/cdn/fonts.googleapis.com/fonts.css`.
   Файлы, скачанные с `?t=…` в имени, переименованы без query (сервер query отбрасывает).
2. Абсолютные `https://sasha-lab.ru/` → относительные.
3. Яндекс.Метрика (счётчик 109777660) заменена заглушкой — копия не льёт хиты
   в реальную статистику владельца оригинала.

Формы Tilda (`ws.tildacdn.com`) в копии не работают — это внешний приёмник, не файл.

### Починка вёрстки 08.09.2026 (третий коммит)
Первая версия зеркала рисовала «кашу»: блоки налезали друг на друга, картинки не
подгружались. Причины и лечение:
4. **Все js/css приехали gzip-ом** (`curl` без `--compressed`, tildacdn отдаёт сжатое) и
   лежали в репо как бинарь — браузер их не исполнял, ни один скрипт Тильды не стартовал,
   а zero-блоки (t396) без JS не расставляются. 33 файла распакованы, в `grab-assets.sh`
   добавлен `--compressed`.
5. **Адреса картинок Тильда собирает на лету**: `static…/<tildXXXX>/f.png` →
   `optim…/<tildXXXX>/-/cover/284x358/…/format/webp/f.png.webp`, размеры зависят от
   вьюпорта — заранее скачать все варианты нельзя. Ходовые варианты лежат в
   `cdn/optim.tildacdn.com/`, на остальные `server.js` отдаёт исходник из
   `static.tildacdn.com` (обрезку и размер задаёт CSS блока).
6. **`wget --convert-links` переписал якоря** `href="#hsblock"` → `href="index.html#hsblock"`,
   из-за чего скрипт-аккордеон не находил кнопку и не сворачивал блок FAQ (страница была
   на 624 px длиннее оригинала). Якоря на свою же страницу возвращены к виду `#…`.
7. Сторонний скрипт вёрстки `cdn.postnikovmd.com/tilda@1.6/` (mods + accordion + css)
   тоже забран в зеркало — от него зависит поведение блоков.

Проверка после починки: поблочное сравнение высот всех `#rec…` копии и оригинала
(1440×1000 и 390×844) — расхождений 0 на всех 5 страницах; битых запросов 0.
Внешними остаются только виджеты Яндекс.Карт/отзывов (iframe) и приём форм.

## База данных (08.09.2026)

Своя база на RU: docker-контейнер **`sashalab-pg`** (postgres:15), слушает только
`127.0.0.1:5446`, том `sashalab-pg-data`, роль и база — `sashalab`. Адрес с паролем —
в `seo/.env` на проде (`SASHALAB_PG_URL`), копия пароля — `/root/.sashalab-pg.pw` на RU.

Что в ней лежит (схема — `db/migrations/001_init.sql`): `questions` (вопросы с формы,
контакт и IP), `materials` (материалы базы знаний — **источник правды вместо
`content/kb/*.md`**), `keywords` (семантика), `positions` (история позиций),
`job_runs` (журнал сбора), `kv`. Общий план проекта — [PLAN.md](PLAN.md).

```bash
node db/migrate.js     # накатить миграции (идемпотентно)
node db/import.js      # затащить в базу content/kb/*.md и старые seo/data/*.json
node content/build.js  # собрать статику ИЗ базы
node seo/cli.js questions --status new
```

Без `SASHALAB_PG_URL` (dev-копия на EU) сборка читает `content/kb/*.md`, а панель и
форма вопроса честно говорят «нет хранилища» — реальные контакты живут только на RU
(152-ФЗ). Файлы в `content/kb/` остаются входом для ручного наполнения: положил
материал — прогнал `node db/import.js`.

**Бэкап:** `/root/backup-sashalab.sh` на RU, cron в 03:40 МСК, дампы
`/root/backups/sashalab_*.sql.gz`, держим 14 штук. Восстановление:
`zcat дамп.sql.gz | docker exec -i sashalab-pg psql -U sashalab -d sashalab`.

## SEO-контур (08.09.2026)

Разбор задачи «держать первую строчку» и критика исходного плана — в
[SEO-PLAN.md](SEO-PLAN.md). Коротко про код:

- `seo/` — модуль работы с поисковиками. Панель собственника на `/seo` под
  паролем (`SEO_ADMIN_PASSWORD`), командная строка `node seo/cli.js`.
  Источники: Wordstat и Search API Яндекса (`YANDEX_SEARCH_API_KEY`,
  `YANDEX_FOLDER_ID`), Яндекс.Вебмастер (`YANDEX_WEBMASTER_TOKEN`),
  Google Search Console (`GSC_KEY_FILE`). Образец окружения — `seo/.env.example`,
  сам `seo/.env` в репозиторий не коммитится.
- `content/kb/*.md` + `node content/build.js` → `dist/` — статическая база
  знаний: страницы вопросов и обзоров с разметкой FAQPage/Article/LocalBusiness,
  перелинковкой, `sitemap-baza.xml` и картой покрытия `coverage.json`.
  Битая внутренняя ссылка роняет сборку.
- `db/` — схема и миграции базы, `db/import.js` — перенос файлов в базу.
- **Вопросы посетителей** (`seo/questions.js`) — форма `/baza/vopros/` без JS,
  обычный POST на `/baza/ask`: ловушка для ботов, ограничение 3 вопроса с адреса
  в час, обязательное согласие на обработку контакта. Вопрос падает в очередь
  панели; владелец пишет ответ там же и жмёт «опубликовать» — материал уезжает
  в таблицу `materials`, база знаний пересобирается, появляется обычная
  статическая страница вопроса. Контакт и IP спросившего на сайт не попадают.
  Это замена «форуму с созданными юзерами» из исходной задачи — почему именно
  такая, написано в [SEO-PLAN.md](SEO-PLAN.md), раздел 1.2.
- `server.js` отдаёт `/baza/` из `dist/`, принимает `POST /baza/ask`, монтирует
  панель и **закрывает всё зеркало от индексации** (`robots.txt` + `X-Robots-Tag: noindex`): копия
  клиентского сайта не должна конкурировать с оригиналом.

Сборка базы знаний обязательна после `git pull` на сервере — `dist/` в git не
хранится, а материалы берутся из базы:

```bash
node content/build.js && pm2 restart sasha-lab --update-env
```

**Материалы, опубликованные из панели, живут в базе на проде, а не в репозитории** —
и это правильное место: раньше они были файлами и их сносил `rsync --delete` с EU.
Выгрузить прод-материалы в файлы (например, чтобы вычитать текст в редакторе):

```bash
ssh -i /root/.ssh/ru_key root@10.10.0.2 \
  "docker exec sashalab-pg pg_dump -U sashalab -d sashalab -t materials --data-only" > /tmp/materials.sql
```

Вопросы посетителей в git не едут вовсе и в файлах больше не лежат: телефоны,
почты и IP живых людей — только в базе на RU.

## Раздел ответов на поисковые запросы — `/baza/otvety/` (18.09.2026)

Статические страницы «один запрос — один ответ»: короткий прямой ответ сверху,
ниже ссылка на подробный разбор в базе знаний. Исходники — `content/otvety/*.md`
(шапка как у материалов плюс `query:` — под какой запрос написан ответ,
и `material:` — на какой разбор ссылаться), сборка та же: `node content/build.js`.

Почему файлы, а не таблица `materials`: материалы владелец публикует из панели
на проде, а ответы раздела пишутся в репозитории и приезжают выкатом.

Сборка не пропустит:
* ответ на несуществующий `material`;
* ответ, чей `query` уже закрыт материалом базы знаний (порог сео-памяти
  `COVERED`) — две свои страницы на один запрос конкурируют между собой;
* дубль адреса внутри раздела.

Спрос НЕ рождает страницы автоматически. Wordstat отвечает, что писать
следующим; текст пишет человек:

```bash
node seo/cli.js wordstat --test     # прогон без API и без денег (фикстура)
node seo/cli.js answers --min 50    # что закрыто ответом/разбором, что в очередь
node seo/cli.js wordstat --clear-test   # убрать тестовые фразы из базы
```

### Пока нет ключа Wordstat

Ключа `YANDEX_SEARCH_API_KEY` / `YANDEX_FOLDER_ID` у проекта нет (попытка входа
09.09.2026 — SEO-PLAN §2.1), а каждый вызов GetTop стоит 20 ₽. Поэтому есть
режим `--test`: ответы Wordstat берутся из `seo/lib/wordstatFixture.js`, строки
ложатся в `keywords` с источником `wordstat-test`, расход не пишется.
**Цифры фикстуры выдуманы и на сайт не попадают ни при каких условиях** —
страницы печатают только написанный человеком текст (сторожит
`test/answers.test.js`). После пополнения аккаунта и получения ключа тот же
`node seo/cli.js wordstat` без `--test` перезапишет фразы настоящими числами.

### Скорость сбора измеряется, а не угадывается (19.09.2026)

```bash
node harvest/run.js probe                 # замер: сколько держит КАЖДЫЙ источник
scripts/harvest-queue.sh --plan           # очередь в порядке из замера, по одному хосту
```

`probe` заходит к источнику примерно 20 раз (меньше минуты): читает `Crawl-delay`
из robots.txt, берёт вразбивку несколько реальных адресов из карты сайта и
прогоняет лесенку пауз 4000 → 2000 → 1000 → 600 → 300 мс. Ступень считается
пройденной, только если ВСЕ ответы 200 и время ответа не выросло в разы против
самой медленной ступени; первый же 429/403/503 или взлёт времени — стоп, дальше
не давим. Рекомендация = последняя прошедшая пауза × 1,5, но **не быстрее
одного запроса в секунду** (`MIN_POLITE`) и не быстрее `Crawl-delay` площадки.
Результат — `seo/data/harvest-speed.json`: пауза, время ответа, сколько страниц
источника уже в базе и сколько часов займёт остаток.

Оттуда же очередь берёт **порядок**: сначала быстрые и почти добранные
источники, самые долгие — в конце. Заход идёт часами, и польза должна
появляться в первые из них, а не в последние.

Сбор идёт медленно намеренно: пауза на источник, потолок страниц за заход,
разбор robots.txt. Быстрее — значит быть закрытым на второй день. «Медленно»
при этом — величина измеренная: 4000 мс всем подряд не вежливость, а лишние
сутки простоя на сайте, который отвечает за 200 мс; а vdf-light.ru поймал 429
и на четырёх секундах — там пауза, наоборот, поднята.
Чужие страницы лежат в `documents` как рабочий материал и **не публикуются**:
на сайт идут только свои формулировки и факты (`vehicles`, `parts`, `fitment`).

`hidplanet.com` (англоязычный форум ретрофита, 64 тысячи тем) взят в особом
режиме `mode:'titles'`: весь html закрыт челленджем Cloudflare, а карта сайта
открыта, и заголовок темы лежит прямо в адресе. Страницы форума не качаются
вообще — в базу попадают только заголовки, которые площадка публикует для
поисковиков. Страницу `/baza/avto/` одни такие факты не рождают: нужен
подтверждённый факт студии либо русскоязычное основание (`content/build.js`).

⚠ Запускать сбор и сборку **от пользователя `sashaweb`**
(`su -s /bin/bash sashaweb -c '…'`): крон живёт под ним, а запуск от root
перекрашивает `dist/` и `.harvest-cache/` в root, после чего крон молча
перестаёт писать. После ручного захода от root — `chown -R sashaweb:sashaweb
/opt/sasha-lab/dist /opt/sasha-lab/.harvest-cache`.

Спрос на автомате — одной командой; на RU стоит в cron вместе со сбором
источников (`scripts/harvest-cron.sh`, вс 03:00 МСК, лог `/var/log/sashalab-harvest.log`):

```bash
npm run seo demand    # Wordstat + Вебмастер + GSC → keywords → сео-память (intents)
npm run seo queue     # что писать дальше и что усилить, вместо новых дублей
```

Ассистент базы знаний: страница `/baza/pomoshnik/`, ручки `POST /baza/assistant`
и `GET /baza/podbor?make=&model=&year=`. Два режима — владелец машины и
установщик. Без `NEURALDEEP_API_KEY` отвечает выдержками из базы, не выдумывая.
